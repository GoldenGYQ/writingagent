# Wiki 知识库上下文能力 TODO

> 状态：Deferred（已记录，暂不开发）  
> 所属方向：写作智能体 / 上下文工程  
> 优先级：在章节式写作、版本管理和基础来源检索稳定之后再评估  
> 本文性质：Feature TODO，不代表当前版本承诺

## 1. 背景

长篇写作不能只依赖聊天历史。用户通常拥有多份原始材料，其中包含重复实体、跨文档概念、相互矛盾的事实和需要持续复用的结论。普通的文档切片检索可以解决“找到相似片段”，但不能完整解决知识归并、关系导航、冲突追踪和人工维护问题。

计划中的 Wiki 知识库能力，是在原始资料与写作智能体之间增加一层可读、可维护、可追溯的知识语义层。用户可以在会话中选择一个或多个 Wiki，写作智能体在限定范围内按任务和章节检索知识，而不是把整个知识库一次性注入模型上下文。

该能力只是上下文工程的一部分，不是写作智能体成立的前置条件。当前应先完成写作项目、章节、版本、ChangeSet、基础 Source Library 和审校闭环。

## 2. 产品目标

- 将原始资料整理为可浏览的来源、实体、概念、问题和综合结论页面；
- 允许用户在对话或写作项目中选择一个或多个 Wiki 作为检索范围；
- 支持显式引用知识页，以及在选定 Wiki 内按需搜索；
- 为检索结果保留原始来源、定位信息和知识库版本；
- 支持写作智能体在规划、起草、核验和审校阶段执行不同粒度的检索；
- 让用户能够查看、修正和维护模型生成的中间知识。

## 3. 非目标

首版不计划：

- 把关系图可视化等同于 GraphRAG；
- 建设通用企业级知识图谱平台；
- 自动相信模型抽取的实体、关系和综合结论；
- 将整个 Wiki 永久放入 system prompt、Session 或长期 Memory；
- 依赖图数据库才能运行；
- 在每次对话中无条件执行昂贵的多跳图检索；
- 替代 Writing Source Library、引用对象和原始证据存储。

## 4. 用户交互

### 4.1 选择知识库

聊天输入区和 Writing Workbench 可以提供 Wiki 多选入口。选择结果表示检索边界，不表示立即把所有内容加入上下文。

会话或写作任务只保存稳定标识：

```json
{
  "selected_wiki_ids": ["project-knowledge"],
  "wiki_versions": {
    "project-knowledge": "v17"
  }
}
```

### 4.2 两种引用模式

#### 模式 A：显式知识页引用

用户明确选择一个知识页时，系统确定性读取该页，并可按 token 预算补充来源片段和受限的一跳关系。该模式不依赖语义召回。

#### 模式 B：知识库范围检索

用户只选择 Wiki 时，写作智能体根据当前任务在选定范围内搜索。推荐采用全文检索、向量检索和受控关系扩展组成的混合检索。

```text
选择 Wiki
  → 保存检索范围
  → 理解当前任务或章节
  → 全文检索 + 向量检索
  → 合并与重排
  → 可选的一跳关系扩展
  → 回到原始来源取证
  → 按 token 预算组装上下文
```

## 5. 建议的知识模型

### 5.1 通用页面类型

- `source`：原始材料的摘要、元数据和定位信息；
- `entity`：人物、组织、产品、工具、数据集等具名对象；
- `concept`：方法、技术、规则、现象和抽象概念；
- `query`：开放问题、资料冲突和待确认事项；
- `comparison`：多个实体或方案的比较；
- `synthesis`：跨来源综合结论；
- `overview`：知识库总览和导航。

### 5.2 写作扩展类型

- `claim`：可写入正文、需要证据支持的主张；
- `evidence`：支持、反驳或限制某个主张的证据；
- `fact`：全文必须保持一致的事实；
- `quote`：带精确定位的原文；
- `style_rule`：术语、语气和格式要求；
- `constraint`：字数、模板、禁用表达和交付要求；
- `outline`：可复用的结构知识；
- `conflict`：来源之间尚未解决的矛盾。

### 5.3 页面最小元数据

```yaml
---
id: concept-authorization-boundary
type: concept
title: 多智能体权限边界
tags: []
related: []
sources: []
created_at: 2026-07-31T00:00:00Z
updated_at: 2026-07-31T00:00:00Z
version: 1
status: draft
---
```

重要事实和主张不能只记录来源文件名，还应尽可能保存：

- `source_id`；
- 页码、章节或 URL fragment；
- 原始切片 ID；
- 内容哈希；
- `supports`、`contradicts` 或 `qualifies` 关系；
- 抽取方式和人工确认状态。

## 6. 知识摄入工作流

建议将智能抽取与确定性校验分开：

1. 保存不可变的原始材料，计算内容哈希；
2. 解析文档结构，生成带定位信息的切片；
3. 识别候选实体、概念、主张和问题；
4. 查询已有索引，完成别名解析和去重；
5. 创建新页面或对已有页面生成合并建议；
6. 提取显式关系，并绑定到原始证据；
7. 校验 frontmatter、链接、来源和悬空节点；
8. 构建全文、向量和图邻接索引；
9. 生成不可变的知识库版本并发布；
10. 记录摄入日志、错误和需要人工确认的项目。

LLM 负责语义抽取、摘要和合并建议；代码负责路径安全、Schema、版本、索引、证据定位和发布一致性。

## 7. 运行时检索策略

### 7.1 推荐策略

- 精确名称、编号和术语优先使用全文/BM25 检索；
- 模糊问题和语义相似内容使用向量检索；
- 图关系只作为受控补充，默认最多扩展一跳；
- 最终用于事实性写作的内容应回到原始来源切片；
- 检索结果应经过合并、去重、重排和 token 预算裁剪；
- 每次运行记录 Wiki 版本、查询、召回页面、来源切片和排序结果。

### 7.2 与写作阶段结合

- 任务分析：检索项目总览、约束、主要实体和开放问题；
- 大纲规划：检索主题关系、综合结论和资料缺口；
- 章节起草：按当前章节目标执行局部检索；
- 事实核验：针对具体主张重新检索原始证据；
- 全文审校：检索术语表、实体表、事实和冲突记录；
- 修改稿件：保留检索记录，并通过 ChangeSet 应用修改。

一次长篇写作不应只在任务开始时执行一次全局 Top-K 检索。

## 10. 与现有写作上下文的边界

Writing Context Provider 仍负责当前项目、文档、章节、大纲、相邻章节摘要、Style Profile 和 ReviewReport。

Wiki Context 只提供与当前任务相关的外部知识：

```text
Writing Context
  = 当前写作状态
  + 用户显式引用的知识页
  + 智能体按需检索的 Wiki 证据
```

Wiki 不替代：

- Session：短期对话历史；
- Memory/Dream：用户偏好和长期记忆；
- Writing Store：稿件、版本和 ChangeSet；
- Source Library：原始资料和正式引用；
- Skill：写作方法和任务步骤。

## 11. 风险

- 模型抽取错误被固化为长期知识；
- 别名解析错误导致实体重复或错误合并；
- 页面关系过密，使图扩展引入噪声；
- 只有文件级来源，没有段落级证据定位；
- 索引与 Markdown 页面版本不一致；
- 原始文档中的提示注入污染摄入和检索上下文；
- 多个 Wiki 同时选择时发生术语和事实冲突；
- 自动综合内容被误当成原始事实；
- 为追求关系图效果而过早引入复杂基础设施。

## 12. 启动条件

满足以下条件后，再把本 TODO 转为实施计划：

- Phase 1 章节式写作闭环已经稳定；
- Source Library 和基础文档切片检索可用；
- 引用可以回溯到原始来源定位；
- 已有真实写作任务证明跨文档知识归并是高频瓶颈；
- 已准备一组可评估的文档、问题、期望召回和写作任务；
- 能明确衡量 Wiki 层相对普通混合 RAG 的实际收益。

建议先做小规模技术验证：同一批资料分别使用“普通混合 RAG”和“Wiki 语义层 + 混合检索”，比较召回质量、事实一致性、引用覆盖率、人工维护成本和写作结果。

## 13. 完成标准

未来实现时，至少满足：

- 用户能创建 Wiki、摄入资料并看到可解释的派生页面；
- 用户能在聊天和 Writing Project 中选择多个 Wiki；
- 显式页面引用具有确定性；
- 普通问题只在选定 Wiki 范围内检索；
- 长篇写作支持按章节重复检索；
- 事实性输出能追溯到原始来源片段；
- 知识页、索引和检索记录均带版本；
- Wiki 内容不会被无上限注入模型上下文；
- 关系图关闭后不影响摄入、检索和写作主流程。
